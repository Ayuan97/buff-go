# buff-go

buff-go 是一个以 Steam 商品为基准，持续采集 Steam 与第三方交易平台行情的私人采集系统。

> 本文定义产品目标和业务边界，不表示仓库当前已经具备下述全部能力。

系统只处理两类市场方向：

- **求购（bid）**：别人愿意出多少钱收购，摘要值取最高求购价 `best_bid`。
- **出售（ask）**：别人愿意以多少钱出售，摘要值取最低出售价 `best_ask`。

Steam 负责定义商品是什么；Steam、BUFF、IGXE 等平台分别提供自己的市场行情。正常行情统一按人民币获取和存储，不在系统内换算其他币种。

## 使用主线

一轮完整使用流程如下：

1. 添加平台账号与访问节点（长/短效、地域、出口验证）。
2. 把账号绑到节点。组合能否干活只看账号平台和节点地域。
3. 在概览按游戏开启各平台方向；Steam 列表采集顺带维护标准商品。
4. 规划器给开着且有健康工人的方向往队尾补货；工人领队头、采一页、再领。
5. 第三方商品映射到 Steam 标准商品，统一最高求购价 / 最低出售价。
6. 运行页看账号加出口 IP 当前在采什么；行情页看最新尝试和历史有效价。
7. 规则命中且详情能力已具备时创建详情任务，否则只记 `detail_unavailable`。

关闭一个方向后停止补货，丢掉该方向未完成任务，已写入行情保留。控制台先显示“停止中”，队列清空且占用释放后才是“已停止”。同一平台另一个方向继续跑。

## 核心业务边界

### Steam 是商品基准

系统为每个 Steam 商品生成内部稳定的 `product_id`，并保留 Steam 返回的原始标识和字段。第三方平台自己的商品 ID 只能映射到 Steam 标准商品，不能反过来修改标准商品身份。

标准商品目录不是单独的采集任务，而是 Steam 列表采集的写入结果：Steam 摘要页面里出现的商品，在提交该页行情的同一事务中写入目录，目录里没有就新建，已有就更新可变字段。目录覆盖哪些游戏由 Steam 采集的 `appid` 范围决定；Steam 两个方向都关闭时不再发现新商品，已写入的目录完整保留。目录只增不减，商品是否还在售由行情状态表达，不靠目录里缺不缺推断。

映射顺序固定为：

1. 优先使用已经验证的 Steam 关联标识。
2. 标识缺失或失效时，在同一个 `appid` 内使用完全一致且唯一的商品名称兜底。
3. 仍然无法唯一确认时整页提交失败，不留下「映射失败」中间状态。

名称兜底不做模糊匹配、跨游戏匹配或本地化名称猜测。

### 摘要先行，详情按需

| 层级 | 采集内容 | 触发方式 |
| --- | --- | --- |
| 摘要采集 | 列表可直接取得的最高求购价、最低出售价和已确认口径的数量 | 长期运行 |
| 详情采集 | 具体订单、订单数量和平台可提供的商品属性 | 后续规则命中后运行 |

第一阶段的核心是稳定采集摘要。详情采集不能无条件遍历全部商品，也不能绕过统一的资源与限频控制。

详情能力按“平台 + 方向”登记，接口证据和适配器实现缺一不可。规则可以命中尚无详情能力的平台行情，但这种命中只能记录为 `detail_unavailable`，不能生成一个永远无法执行的详情任务。

### 账号和访问节点：组合即工人

访问节点是网络出口（本机直连或代理），属性包括：

- **时效**：长效（固定出口与失效时间）或短效（池化 IP，用着期间 IP 不变；寿命不一靠探测，失败则丢弃）。
- **地域**：国内 / 国外 / 香港（本机也必须选）。国内节点只打国内站，国外节点只打国外站，香港两类都可。
- **平台线路**：Steam = 国外站 → 只用国外/香港节点（**国内节点不能采 Steam**）；BUFF、IGXE = 国内站 → 只用国内/香港节点（**国外节点不能采国内站**）。
- **短效补货**：多家代理商；按地域配置最少可用短效数，不足则按商优先级补到该数。出口可用、绑了对应平台账号、地域允许该平台，就可以领任务。

组合 = 账号绑到节点。采集只校验账号可用、节点可用、节点地域允许该平台。

不设手填的「并行数」。并发 = 健康工人数。方向队列水位 100 是备货，不是并发。同一账号同时只打一枪。同一节点可同时绑不同平台的账号（各走各平台限流）。

每个开启的方向有一条有序任务队列。规划器在有健康工人且队列低于水位时往队尾补货；工人从能干的方向领入队最早的队头。认领超时回队。429 不丢任务。出售返回美元或 302 登录时标账号失效，任务回队。

限频按平台隔离；出口相关键必须带平台维度（平台+出口 IP、平台+账号+出口 IP）。同平台内多节点同出口则共享该平台 IP 预算。节点启用前验证出口 IP 与有效期；验证失败或过期时该节点上的工人停领。短效仅因出口/连接探测失败丢弃，不用平台业务错误（如 429、Cookie 失效）当代理死亡。

### 行情必须可解释

- 金额只接受明确的人民币数据，并使用人民币分整数保存。
- 求购保存最高求购价，出售保存最低出售价，两者不能混用。
- 订单数量与商品件数只有在平台语义已经确认后才保存。
- 平台数据时间与本系统采集时间分别记录。
- 有行情、确实为空、接口不支持和采集失败必须区分，不能都写成价格 `0`。
- 已提交的行情页保留；当前页每方向只留最新一页。

统一行情以“Steam 标准商品 + 平台 + 方向”为唯一身份。最近一次采集尝试的状态与最近一次有效价格分别保存：较新尝试失败、为空或不可用时，旧价格只能作为带原采集时间的历史有效值展示，不能继续冒充当前有效行情。未覆盖商品不能被批量改成失败；已关闭开关版本和较旧 `write_seq` 不能覆盖较新的结果。

## 系统形态

系统采用 Go 模块化单体作为采集与控制后端，配套 TypeScript Web 控制台，并由 PostgreSQL 保存配置、运行状态和业务数据。生产运行只需要一个 Go 进程；Web 静态文件由该进程提供，不额外运行 Node 服务。具体模块、依赖和目标目录见 [系统架构](./docs/ARCHITECTURE.md)。

## 产品验收标准

- Steam 商品始终是跨平台商品身份基准，映射失败不会污染标准目录。
- 每个平台的求购和出售可以独立开启、关闭；控制台能区分期望状态与实际运行状态。
- 标准商品目录由 Steam 列表采集顺带维护：列表中的新商品自动入库，不存在独立的目录任务和目录开关。
- 账号绑到节点即可成为工人；路由只看平台和地域。不手填并行数，并发等于健康工人数。
- 节点区分长效/短效与国内/国外/香港；短效按地域水位多商补货；本机与代理同一套验证与调度。
- 同一平台账号同时只服务一条任务；同一节点可同时绑不同平台的账号。认领占用写在队列表里。
- 各平台限频与冷却独立；键含平台维度，Steam 限流不写到 BUFF/IGXE。
- 所有可比较行情都是人民币分整数，最高求购价和最低出售价语义固定。
- 空行情、接口不支持和采集失败明确区分；已提交行情不会因为后续失败被回滚。
- 控制台可以看到行情时间、工人当前页、资源占用、冷却和失败原因。
- 只有命中规则的商品进入详情采集，部分详情不会被展示为完整订单列表。
- 程序重启后从 PostgreSQL 恢复开关、组合、冷却和方向队列；超时认领回队。
