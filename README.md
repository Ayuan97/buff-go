# buff-go

buff-go 是一个以 Steam 商品为基准，持续采集 Steam 与第三方交易平台行情的私人采集系统。

> 本文定义产品目标和业务边界，不表示仓库当前已经具备下述全部能力。

系统只处理两类市场方向；Steam 商品目录同步是独立维护任务，不属于市场方向：

- **求购（bid）**：别人愿意出多少钱收购，摘要值取最高求购价 `best_bid`。
- **出售（ask）**：别人愿意以多少钱出售，摘要值取最低出售价 `best_ask`。

Steam 负责定义商品是什么；Steam、BUFF、IGXE 等平台分别提供自己的市场行情。正常行情统一按人民币获取和存储，不在系统内换算其他币种。

## 使用主线

一轮完整使用流程如下：

1. 使用者在 Web 控制台添加平台账号和访问节点，并建立明确的账号与节点组合。
2. 使用者为目标游戏开启独立的 Steam 商品目录同步；系统使用 Steam 的账号节点组合建立并周期更新标准商品目录。
3. 使用者分别开启某个平台的求购或出售采集，例如只开启 Steam 出售和 BUFF 出售。
4. 系统只为已开启的方向创建任务；每个页面请求独占一个可用的“登录账号 + 访问节点”组合，请求处理完成后释放。
5. 平台采集器在限频允许时分页读取列表行情，每完成一页就规整并保存数据、游标和覆盖范围。
6. 第三方平台商品映射到 Steam 标准商品，形成统一的最高求购价或最低出售价。
7. 控制台展示最新行情、数据时间、采集完整性、资源占用、冷却状态和失败原因。
8. 后续规则命中摘要行情，并且对应平台与方向的详情能力已经验证和实现时，系统才创建订单详情任务；否则只记录命中和“详情不可用”。

关闭采集后，系统立即停止创建新请求，并取消可以取消的在途请求。控制台先显示“停止中”，待该方向的任务、在途请求和执行占用释放后才显示“已停止”；同一平台另一个方向可以继续运行。已成功保存的页面继续保留，运行结果和数据完整性分别记录，部分采集不能冒充完整结果。

## 核心业务边界

### Steam 是商品基准

系统为每个 Steam 商品生成内部稳定的 `product_id`，并保留 Steam 返回的原始标识和字段。第三方平台自己的商品 ID 只能映射到 Steam 标准商品，不能反过来修改标准商品身份。

映射顺序固定为：

1. 优先使用已经验证的 Steam 关联标识。
2. 标识缺失或失效时，在同一个 `appid` 内使用完全一致且唯一的商品名称兜底。
3. 仍然无法唯一确认时，记录失败原因并暂不处理该商品。

名称兜底不做模糊匹配、跨游戏匹配或本地化名称猜测。

### 摘要先行，详情按需

| 层级 | 采集内容 | 触发方式 |
| --- | --- | --- |
| 摘要采集 | 列表可直接取得的最高求购价、最低出售价和已确认口径的数量 | 长期运行 |
| 详情采集 | 具体订单、订单数量和平台可提供的商品属性 | 后续规则命中后运行 |

第一阶段的核心是稳定采集摘要。详情采集不能无条件遍历全部商品，也不能绕过统一的资源与限频控制。

详情能力按“平台 + 方向”登记，接口证据和适配器实现缺一不可。规则可以命中尚无详情能力的平台行情，但这种命中只能记录为 `detail_unavailable`，不能生成一个永远无法执行的详情任务。

### 账号和访问节点共同执行请求

本机直连也作为一个访问节点参与分配。节点有固定地域能力：国内节点只访问国内接口，国外节点只访问国外接口，香港节点可以访问两类接口；本机部署时也必须明确选择一种地域能力。

节点按平台独占分配，不在平台之间自动借用。同一平台的求购和出售共享该平台的账号、节点和总限频预算。第一版使用明确的“平台账号 + 访问节点”组合执行页面请求，同一账号和节点不会被并发请求重复占用。

一个平台的有效并发数不等于已分配节点数，而是受可用账号数、已分配节点数、可用账号节点组合数、限频和当前可并行工作共同限制。不同游戏、方向、摘要任务和详情任务可以在不同组合上并行；同一顺序游标的分页流默认逐页执行，只有平台证据证明分页可安全拆分后才允许并发分页。如果 Steam 只有一个可用账号，即使分配两个节点，首版也只有一个有效并发组合。

不同平台、接口、账号、IP 和账号与 IP 组合可以有不同的频率与冷却状态。具体数值必须在接入平台时通过受控探测确认，不能从 Steam 的结果推测 BUFF 或 IGXE。

首版访问节点只接受固定出口 IP 或能保持粘性会话的代理。节点启用前记录实际出口 IP 和验证有效期，限频和冷却使用真实出口 IP 而不是节点 ID；多个节点共享同一出口时也共享 IP 预算。验证到期、代理地址或凭据变化、粘性会话重建时先停止派发并重新验证；新出口确认前节点不能参与采集。

### 行情必须可解释

- 金额只接受明确的人民币数据，并使用人民币分整数保存。
- 求购保存最高求购价，出售保存最低出售价，两者不能混用。
- 订单数量与商品件数只有在平台语义已经确认后才保存。
- 平台数据时间与本系统采集时间分别记录。
- 有行情、确实为空、接口不支持和采集失败必须区分，不能都写成价格 `0`。
- 分页中断后保留已完成页面，并明确显示覆盖不完整。

统一行情以“Steam 标准商品 + 平台 + 方向”为唯一身份。最近一次采集尝试的状态与最近一次有效价格分别保存：新一轮失败、为空或不可用时，旧价格只能作为带原采集时间的历史有效值展示，不能继续冒充当前有效行情。部分运行不能把未覆盖商品批量改成失败；旧运行、已关闭开关版本和迟到响应不能覆盖较新的结果。

## 系统形态

系统采用 Go 模块化单体作为采集与控制后端，配套 TypeScript Web 控制台，并由 PostgreSQL 保存配置、运行状态和业务数据。生产运行只需要一个 Go 进程；Web 静态文件由该进程提供，不额外运行 Node 服务。具体模块、依赖和目标目录见 [系统架构](./docs/ARCHITECTURE.md)。

## 产品验收标准

- Steam 商品始终是跨平台商品身份基准，映射失败不会污染标准目录。
- 每个平台的求购和出售可以独立开启、关闭；控制台能区分期望状态与实际运行状态。
- Steam 商品目录同步可以独立启停和周期运行，不依赖求购或出售开关。
- 使用者可以添加、删除和查看平台账号与访问节点，并明确完成平台分配和账号节点组合。
- 节点只被一个平台独占分配，本机直连与代理遵守同一套调度规则。
- 同一个账号或节点不会被并发任务重复占用，关闭任务后资源能够可靠释放。
- 平台、接口、账号、IP 和组合的频率及冷却可以分别生效，平台之间不会错误连带。
- 所有可比较行情都是人民币分整数，最高求购价和最低出售价语义固定。
- 空行情、接口不支持和采集失败明确区分；分页中断不会丢失已经完成的数据。
- 控制台可以看到行情时间、运行状态、覆盖完整性、资源占用、冷却和失败原因。
- 只有命中规则的商品进入详情采集，部分详情不会被展示为完整订单列表。
- 程序重启后能够从 PostgreSQL 恢复必要配置、冷却状态和未完成运行上下文。
